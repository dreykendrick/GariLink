# User action required

Only the actions below require credentials, identity, or hardware Codex cannot
safely invent. Complete them locally; never commit secrets.

## Confirm permanent Android identity and company ownership

### Action

Confirm that `ke.co.garilink.garilink_mobile` is the permanent Play Store package ID and
that the installed name `GariLink` is final. Ensure Supabase, Play Console, Beem, monitoring,
and signing materials are owned by company-controlled accounts with at least two recovery
administrators where supported.

### Why

The package ID cannot be changed for an existing Play application. Operational assets must
not depend on one developer laptop or personal account.

## Select and configure crash monitoring

### Action

Create one company-owned Sentry or Firebase Crashlytics project, approve its privacy/data
handling, and provide its non-secret project configuration through the protected release
environment. Do not paste credentials into chat.

### Why

The app already has a privacy-safe uncaught-error boundary, but no external event sink is
configured. A controlled non-PII smoke event must be received before rollout.

## Verify backups and perform an isolated restore drill

### Action

Confirm the GariLink Supabase plan's actual backup frequency and retention, create an
encrypted pre-release export, and execute `BACKUP_RESTORE_RUNBOOK.md` against a separate
temporary project.

### Why

Hosted backup availability and successful restoration cannot be inferred from repository
code. The production database must never be used as a destructive restore target.

## Beem Production SMS

### Action

Obtain an approved Beem sender name and production API credentials, then store
them as Supabase Edge Function secrets for project `yvcdkmsfuakjflmuatgz`.

### Why

Registration, phone verification, resend, and password recovery intentionally
fail closed until the real SMS provider is configured.

### Exact requirement

- `BEEM_API_KEY`
- `BEEM_SECRET_KEY`
- `BEEM_SENDER_ID`
- `SEND_SMS_HOOK_SECRET` generated by Supabase when configuring the Send SMS hook

Deploy `beem-sms`, configure its HTTPS URL as the Supabase Auth Send SMS hook,
and use the matching signing secret on both sides.

### Security warning

Do not paste these values into chat, source files, screenshots, or issue trackers.
Use `supabase secrets set` locally or the protected Supabase dashboard secret UI.

### How Codex will use it

It enables controlled registration, resend, invalid/expired-code, rate-limit, and
password-recovery tests with a Tanzanian test number.

## Configure Android production signing

### Action

Create or select the long-lived GariLink upload keystore. Copy
`mobile_flutter/android/key.properties.example` to the ignored
`mobile_flutter/android/key.properties` and replace every placeholder locally,
or set the four documented `GARILINK_KEYSTORE_*` environment variables.

### Why

The private signing key and passwords must be owned and backed up by the product
owner. The build now refuses to create a release APK when they are missing.

### Exact requirement

- `GARILINK_KEYSTORE_FILE`
- `GARILINK_KEYSTORE_PASSWORD`
- `GARILINK_KEY_ALIAS`
- `GARILINK_KEY_PASSWORD`

### Security warning

Never commit the keystore, `key.properties`, passwords, or recovery material.
Keep two encrypted backups controlled by the product owner.

### How Codex will use it

It enables a current signed release build and signature verification.

## Supply the GariLink database password locally

### Action

Reset the dedicated project's database password in Supabase if the generated
password was not retained, then run `supabase link --project-ref yvcdkmsfuakjflmuatgz`
from the repository's `supabase` directory.

### Why

The hosted schema, including rentals, is represented by ordered source migrations,
but durable CLI linking, local SQL assertion runs, and future
`supabase db push` verification require the database password.

### Security warning

Do not paste the password into chat or commit it. Enter it only in the CLI prompt
or your protected deployment secret store.

### How Codex will use it

It enables migration-drift checks and reproducible database deployment validation.

## Run physical Android acceptance tests

### Action

Install the newly built debug APK on a clean Android device and execute
`DEVICE_QA_CHECKLIST.md`; repeat with the signed release artifact before launch.

### Why

TalkBack, keyboard behavior, SMS delivery, process death, connectivity changes,
and device-specific layout/performance cannot be proven by widget tests.

### Exact requirement

One supported small-screen Android device, one representative standard device,
a controlled Tanzanian phone number, and access to device logs with secrets redacted.

### Security warning

Use dedicated test accounts. Do not share OTPs, access tokens, or unredacted logs.

### How Codex will use it

Results close or identify the remaining device, accessibility, and live-service gates.

For Sprint 1, include a real owner listing with 10 mixed JPEG/PNG/WebP source
photos. Verify selection, compression, progress, retry after airplane mode,
cover changes, ordering, deletion, card thumbnails, gallery swiping, fullscreen
zoom, and a broken-image fallback. Also verify that a second workspace cannot
change or delete the first workspace's media. This live account/device pass is
the remaining validation that cannot be performed without user-owned test
credentials and attached Android hardware.
